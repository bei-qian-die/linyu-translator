### 失败路径（都实际跑过）

1. **百度百科移动端（`wapbaike`）**：页面能取、`bkimg` 图床带百度 Referer 也能下（403 的根因是 Referer 用了 bilibili），但**张冠李戴率极高**：花火→穿和服的真人群像、砂金→画架前的画家、刃→书法字「刃」、椒丘→纯文字卡、星期日→写着「星期天」的图、镜流→遗器推荐信息图、桂乃芬→配队攻略图。第一批 29 张出联系表后基本全废，整批弃用。
2. **B 站检索接口**：`api.bilibili.com/x/web-interface/search/type` 本轮持续返回 `412 request was banned`，退避重试 3 次仍未解除；这是最理想的图源（官方角色 PV 封面），可惜用不上。
3. **360 图片检索**：可用，但候选大量是攻略信息图 / 横幅图；加「标题必须含角色名 + 所属游戏」「宽高比 ≤1.6」「最短边 ≥280px」三道过滤后才勉强可用。
4. **萌娘百科 / fandom / 百度图库**：延续 1.39.0 的结论，仍然不通，未重复踩。

### 包体为什么会顶到 2MB

`pkg-hero` 上轮已是 1.94MB，只剩 60KB 余量；本轮 800+ 条目的中文正文按 UTF-8 约 3 字节/字，原样放进去直接 2.07MB。

处理顺序：

1. 先做「精简落库」：长释义取到句号、alias 只留常用写法、条数收口到指标线 —— 只省下约 13KB，不够。
2. 改结构性方案：extra27 真实数据放主包 `miniprogram/data/lore-extra27.js`，分包 `pkg-hero/data/lore-extra27.js` 只留 ≤100 字节转发（微信允许分包 require 主包，反过来不行）。
3. 结果主包 1.54MB / 分包 1.94MB，均低于 2MB，且内容一点没删（词卡 250、英雄 30、名言 150 全部在）。
